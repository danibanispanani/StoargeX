# Domain Foundation Phase

## Status and scope

This phase establishes the additive data and service foundation requested for the StorageX beta rebuild. It does not replace an existing workflow, migrate legacy free text, delete production data, reconstruct UI, or change subscription tariffs.

The implementation deliberately extends the existing deep modules: `DocumentSequence`, purchases and owned lots, movement-based inventory, sale and return allocations, debts, imports/provenance, audit, and the existing subscription tier. New UI and complete mutation workflows remain later, separately reviewed work.

## Architecture decision summary

| Capability | Existing model extended | Additive foundation | Compatibility boundary |
|---|---|---|---|
| Business partners | `Purchase`, `ConsignmentLot` | `BusinessPartner`, `BusinessPartnerRole` | `Purchase.vendor`, lot vendor/owner fields and other historical labels remain readable snapshots. Partner references are nullable. |
| Platform accounts | `Platform`, `Sale`, `Credential` | `MarketplaceAccount` | A sale may continue to reference only `Platform`. Account metadata may not contain secrets; credentials remain in the credential vault. |
| Payout/payment accounts | `Sale`, `Purchase` | `PayoutAccount` | Existing payout recipient/payment labels remain untouched and readable. New references are nullable. |
| Item condition | `StockItem`, `InventoryPosition`, `ReturnLine` | `ItemCondition` enum plus mapping service | Existing `condition` strings are retained. Unknown legacy values intentionally map to `null`, never to a guessed condition. |
| Expenses | None replaced | `ExpenseCategory`, `Expense`, `ExpenseRecurrenceRule` | A recurrence rule belongs to a base expense; no occurrences are generated by this phase. Import provenance uses the existing generic `SourceReference` target mechanism. |
| Supplier returns | Purchase and inventory foundations | `SupplierReturn`, `SupplierReturnLine`, `SUPPLIER_RETURN_OUT` movement type | Customer `Return`, `ReturnLine`, `ReturnAllocation`, and their service remain unchanged. Supplier-return lines point to purchase lines, inventory positions, and an optional outbound movement. |
| Tasks | Existing `Task.assigneeId` | Nullable task scope, progress, `TaskAssignment`, `TaskChecklistItem`, `TaskActivity` | The legacy single assignee remains present. Tasks with `scope = null` remain valid until deliberately classified. |
| Fees | `Platform` | `FeeSchedule`, versioned `FeeRule` | Rules can be platform-wide or account/category/condition-specific. Validity uses `[validFrom, validUntil)`. This phase does not alter sale calculations. |
| Feature access | `Organization.subscriptionTier` | `FeatureEntitlement` | Tiers remain intact. `BUSINESS` continues to grant consignment through the compatibility map; dated subscription/add-on/trial/manual grants can be added. Visibility never controls data retention. |

## Model contracts

### Business partners

`BusinessPartner` is organization-owned master data with controlled display/legal names, optional contact/source references, notes, active state, and non-secret metadata. Roles classify the same partner as supplier, consignment partner, customer, or other without duplicating the partner. Purchases and consignment lots receive nullable references; their existing text remains the historical snapshot.

### Platforms, accounts, and payout accounts

`MarketplaceAccount` is always below one existing `Platform` and one organization. It carries a display name, optional external account identifier, account type, active state, optional default payout account and fee schedule, and metadata without secrets. `Sale` and `Credential` receive nullable account references, so existing platform-only records remain valid.

`PayoutAccount` covers bank, PayPal, platform wallet, shareholder-private, and other accounts. It can optionally reference a business partner and is available to sales, purchases, expenses, and marketplace-account defaults. Historical payout-recipient strings are not rewritten.

### Condition compatibility

The canonical values are `NEW`, `OPEN_BOX`, `REFURBISHED`, `USED`, and `DEFECTIVE`. The condition service normalizes a conservative alias set. Explicit canonical values take precedence over legacy strings. Unrecognized inputs return `null`, preserving the original source text for review and future mapping expansion.

### Expenses and recurrence

Expenses record category, optional supplier and payment account, occurrence date, gross/net/tax values, receipt reference, notes, and posting status. The optional one-to-one recurrence rule supports day, week, month, quarter, and year intervals, an interval multiplier, optional external rule text, start/end dates, next occurrence, and active state.

The recurrence service uses UTC arithmetic and clamps month/year transitions to the target month's last day. A missing or inactive rule produces no next occurrence. The SQL migration enforces positive intervals, non-negative monetary/tax components, and valid date order.

### Supplier returns

Supplier returns are independent of customer returns. A header belongs to a purchase, retains a mandatory supplier text snapshot, may reference a normalized supplier, receives its own document kind, and owns lines. Each line points to a purchase line and inventory position and may link exactly one `InventoryMovement(SUPPLIER_RETURN_OUT)` as the stock evidence.

No supplier-return mutation service or UI is introduced here. A later workflow must create the outbound movement through the existing inventory service and attach it transactionally; it must not overwrite inventory counters directly.

### Tasks

Assignments support one primary assignee and multiple collaborators. SQL enforces at most one primary assignment per task. The central invariant service additionally enforces same-tenant assignments, unique users, exactly one primary for a personal task, and one primary for an assigned team task. An unassigned team task is permitted as a planning state. Checklists and activities retain organization ownership and actor/completer provenance.

### Versioned fees

Fee rules carry platform, optional account/schedule/category/condition scope, validity dates, percentage and fixed components, optional minimum/maximum, advertising and payment components, VAT treatment, priority, origin (`MANUAL`, `IMPORTED`, `SYNCED`), source, and metadata. The selector first filters by tenant and scope, then orders by priority, specificity, version start, and stable ID. It is a policy foundation only; existing calculations are not replaced.

### Feature entitlements

Entitlements are organization-owned dated grants with feature key, lifecycle status, source (`SUBSCRIPTION`, `ADD_ON`, `TRIAL`, `MANUAL`), optional external reference, and non-secret metadata. A grant is active only when its status is `ACTIVE`, its start is reached, and its exclusive end has not been reached.

The current compatibility map grants `CONSIGNMENT` to `BUSINESS` organizations even if no entitlement row exists. This preserves existing tier behavior while allowing later additive grants. An inactive or expired add-on never deletes or mutates consignment data.

## Migration safety

Migration `20260713100000_beta_domain_entitlements` is additive:

- it creates new enum values, tables, indexes, foreign keys, checks, and RLS policies;
- it adds only nullable columns, except `Task.progressPercent`, which has the safe default `0`;
- it does not drop or rename a model, table, column, enum value, index, or constraint;
- it performs no data rewrite or forced legacy backfill;
- delete behavior is explicit: master-data references generally use `SET NULL`, owned child records use `CASCADE`, and posted purchase/inventory/user evidence uses `RESTRICT` where deletion would make history incoherent;
- every new tenant table has a required indexed `organization_id`, organization foreign key, `ENABLE/FORCE ROW LEVEL SECURITY`, tenant `USING`/`WITH CHECK`, and the established controlled bypass policy;
- SQL checks cover monetary ranges, recurrence/date order, return quantities, task progress/checklist consistency, fee ranges, entitlement dates, and the single-primary task invariant.

The generated Prisma SQL was hand-reviewed and then extended only for invariants and RLS that the Prisma schema cannot express. Deployment must still run through the normal reviewed migration process. No production database was mutated during this phase.

## Central service boundaries

- `feature-entitlement-service`: evaluates dated grants and the legacy tier compatibility map without coupling route/UI code to storage details.
- `marketplace-account-service`: resolves only active accounts within the requested organization and platform; ambiguity requires an explicit account.
- `expense-recurrence-service`: classifies one-time/recurring expenses and computes the next safe occurrence.
- `condition-service`: maps known legacy labels conservatively and preserves unknowns for review.
- `fee-rule-service`: validates effective scope/time and deterministically selects a rule.
- `task-assignment-service`: owns assignment cardinality and tenant invariants.

These are intentionally narrow policy modules. They do not introduce a second purchase, inventory, sale, return, debt, import, or calculation implementation.

## Test strategy

Focused unit coverage verifies:

- active, inactive, future, expired, trial, cross-tenant, and legacy-tier entitlement decisions;
- fee validity windows, tenant/account/category/condition scope, priority, and specificity;
- known and unknown condition mappings;
- one-time, daily, weekly, month-end, and ended expense recurrence;
- platform-account tenant/platform resolution and ambiguity;
- personal/team task assignment, one-primary, duplicate-user, and tenant invariants;
- the presence of required organization columns and the RLS contract for every new tenant model;
- compatibility of the expanded document kind and nullable inventory condition with existing fixtures.

The RLS test is a deterministic migration contract test. A database-backed RLS execution check remains part of deployment verification in an environment where the migration is applied.

## Deferred work

This phase intentionally does not include:

- backfilling partner, account, payout, condition, or task references;
- expense, supplier-return, fee-management, task, or entitlement UI;
- supplier-return mutation/posting logic;
- applying fee rules to existing sale calculations;
- route/navigation entitlement enforcement or tariff changes;
- recurring-expense materialization jobs;
- new import commit pipelines, templates, or exports.

When any of those modules becomes importable, it must reuse `ImportBatch` and `SourceReference` and provide a downloadable template, validation, dry run, row-level errors, review, and commit as required by the product constitution.
